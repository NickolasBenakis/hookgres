Open-source Postgres webhooks for TypeScript

Webhooks that commit with your data.

A TypeScript library that queues webhooks in your Postgres transaction, then signs, retries and logs every delivery. No extra service, no per‑message bill.

Add Hookgres (https://hookgres.dev) to this project so we can send signed webhooks to our customers. First read https://hookgres.dev/llms.txt. Then install hookgres and pg, run migrate() on startup, start the delivery worker with a graceful shutdown, add API routes for customers to manage their webhook endpoints scoped to their tenant, and call send() inside our existing database transactions where events happen. Pass blockPrivateAddresses: true so customer URLs can't reach private or internal addresses.

Get started Try the playground 
import { Hookgres } from "hookgres";

const hookgres = new Hookgres({
  connectionString: process.env.DATABASE_URL,
});
await hookgres.migrate();
hookgres.start();

// Your customer registers an endpoint
await hookgres.createEndpoint({
  tenantId: "acme",
  url: "https://acme.com/webhooks",
  eventTypes: ["invoice.paid"],
});

// In your transaction: sent only if it commits
await hookgres.send({
  tenantId: "acme",
  eventType: "invoice.paid",
  payload: { invoiceId: "in_123", amount: 4200 },
}, { client });
import { verifyWebhook } from "hookgres";

// Your customer's server. Any Standard Webhooks
// library verifies these requests too.
export async function POST(request: Request) {
  try {
    const event = verifyWebhook({
      secret: process.env.WEBHOOK_SECRET!,
      headers: request.headers,
      body: await request.text(),
    });
    // event.type === "invoice.paid"
    return new Response(null, { status: 204 });
  } catch {
    return new Response(null, { status: 400 });
  }
}

  • Transactional send

    Pass your client to send(). Roll back and nothing goes out.

  • Standard Webhooks

    HMAC-SHA256 signatures the official verifiers in 9 languages accept.

  • Retries for 28 hours

    8 attempts, 5 seconds to 10 hours apart, then the delivery fails.

  • Endpoint API

    Create, list, update and disable endpoints per tenant and event type.

  • Log and replay

    Every attempt is a row in your database. replayDelivery() resends.

  • Secret rotation

    Old and new secrets both sign for 24 hours, so receivers never miss one.

The six cases, with code

hookgres.send()

One commit in. Every endpoint, signed and retried.

send() writes a row next to your data. After COMMIT, workers claim it with SKIP LOCKED, sign the request and deliver it to each endpoint. A failure goes back on the schedule.

BEGIN … COMMIT

Queued in your transaction. Sent only if it commits.

A webhook service is a second system. Call it after your commit, and a crash in between loses the event. Call it before, and a rollback leaves your customer with a webhook for an invoice that was never paid. Hookgres writes the webhook in the same transaction as your data, so you get the outbox and the delivery in one library.

On an ORM, pass its transaction instead. Adapters for Prisma and Kysely ship with Hookgres; Drizzle, postgres.js, Knex, Sequelize, TypeORM and MikroORM each take a tested wrapper of a few lines.

Waiting for the transaction

Nothing is sent until the transaction commits.

ROLLBACK

A job queue can’t roll back with your data.

A queue outside Postgres keeps a job your transaction rolled back, so your customer hears about a payment that never happened. Two terminal recordings with real Postgres and the published package.

How it works

The same payment code, run twice. With BullMQ, the payment rolls back but the job is already in Redis, so acme.com marks in_124 paid. With hookgres.send(), the webhook rolls back with the payment.

From npm install hookgres pg to a logged retry, against a receiver that is down for two attempts. The rolled-back invoice sends nothing; the committed one is signed, retried and logged.

Not a contrived example. Other teams hit these bugs in 2026:

Animation of one event sent to three endpoints. The healthy one answers 204 on the first attempt. The flaky one answers 503 twice, then 204 on the third attempt, 5 minutes in. The one that is down answers 500 to all eight attempts over 27.6 hours and the delivery fails.

A server that’s down never holds up the others. Each endpoint gets its own delivery, its own retries and its own log rows.

standard webhooks

Your customers verify it with code they already have.

Every request is signed to the open Standard Webhooks spec. Your customers check it with an official library in their own language, so you never have to invent a signing scheme and support it.

Official libraries for JavaScript, Python, Go, Ruby, PHP, Rust, Java, C# and Elixir. Hookgres’s tests check its signatures against the JavaScript one.

hookgres.deliveries

Every attempt is a row you can query.

Status, response body and timing for each request, stored next to your data. A customer-facing log or a support view is one SQL query away.

select d.id, m.event_type, d.status, d.attempt_count,
       m.created_at::time(0) as sent_at
from hookgres.deliveries d
join hookgres.messages m on m.id = d.message_id
where m.tenant_id = 'acme'
order by m.created_at desc limit 4;

  • Replay. replayDelivery() re-sends a finished delivery with the same webhook-id, so receivers can deduplicate.
  • Idempotency keys. Pass the same key twice and get the original message back, not a duplicate.
  • Built for multi-tenant apps. Every event goes only to one tenant’s endpoints, filtered by event type.
  • Crash recovery. If a worker dies mid-request, its claim expires and another worker picks it up.

library vs. hosted service

A library, not a service.

Hosted services like Svix and Hookdeck make sense when you want someone else to run it. Hookgres fits when you’d rather keep webhooks next to your data.
